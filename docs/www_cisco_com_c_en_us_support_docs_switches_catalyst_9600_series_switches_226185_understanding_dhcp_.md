## Introduction
This document describes the DHCP snooping interactions and behaviour when the packet is crossing any L3 device and if the packet is encapsulated in L3 header.
## Prerequisites
### Requirements
Cisco recommends that you have knowledge of these topics:
  * Cisco IOS® XE proficiency in configuration and operational commands.
  * Familiarity with the Cisco Catalyst 9000 series switch hardware and architecture.
  * A solid understanding of DHCP protocol operations and DHCP snooping mechanisms.
  * A conceptual understanding of DHCP option 82 and the role of the relay agent.
  * Basic Routing protocol knowledge.


###    
Components Used
The information in this document is based on these software and hardware versions:
  * Core/Distribution switch: Cisco Catalyst 9600X series
  * Access switch: Cisco Catalyst 9300 series
  * DHCP client: End-host device
  * DHCP server: Centralised network service provider


The information in this document was created from the devices in a specific lab environment. All of the devices used in this document started with a cleared (default) configuration. If your network is live, ensure that you understand the potential impact of any command.
## Background Information
This document examines how DHCP snooping inspects and intercepts DHCP packets as they traverse a Layer 3 hop. Using practical configuration examples and analysis of related packet captures, it demonstrates the interaction of DHCP snooping on Layer 3 hops within a Cisco Catalyst 9000 series network environment.

Here there is no trust from DHCP snooping end and OFFER is entering, then why is the Offer not getting dropped on an untrusted port?
  
As you know, in a network where DHCP Snooping is enabled, ports are categorised as either trusted or untrusted.
Trusted Ports are connected to legitimate DHCP servers or other trusted switches. All DHCP messages are allowed on it.  
Untrusted Ports are typically connected to end-user devices (clients). They are restricted to prevent "DHCP Spoofing" or "Rogue DHCP Server" attacks.  
DHCP Offer and DHCP ACK packets are considered 'server-side' messages. According to security rules, these messages must only ever originate from a legitimate server.  
When a DHCP relay agent or any L3 Router/Switch receives a DHCP Offer on a L2 port configured as untrusted, the DHCP Snooping mechanism identifies this as a security violation. It assumes that a rogue DHCP server is attempting to provide unauthorised IP addresses to clients on the network.  
Even though the packet is unicast (directed specifically to the relay agent), the trust state of the physical or logical port takes precedence. The security check is performed on the port level regardless of whether the packet is broadcast or unicast.  
Because the port is untrusted, the system will block the DHCP Offer to protect the network from potentially malicious or incorrect configuration data coming from an unauthorised source.
An L3 port (a routed interface) operates at Layer 3. Because it is a routed interface, it does not observe the L2 DHCP Snooping trust/untrust rules that apply to switchports.  
A client sends a broadcast request. The Relay Agent (the L3 device) intercepts this and sends an unicast request to the DHCP server.  
The DHCP server sends an unicast DHCP Offer back to the IP address of the Relay Agent (specifically to the giaddr or Gateway IP address).  
When the packet arrives at the L3 port of the Relay Agent or on any L3 hop in the packet path, the device accepts the packet as legitimate routing traffic.  
Unlike the earlier scenario (an L2 untrusted port), where the switch is looking for 'server-side' messages coming from a client-facing port, the L3 port is acting as the intended destination or legitimate L3 hop for the response of the server.  
If L3 ports dropped unicast DHCP offers, DHCP relaying mechanism will never work, as the server will never be able to communicate back to the relay agent.
Finally the Offer packet will traverse till it reaches the client.

## Summary
Refer to this table in order to understand the packet forwarding scenarios.  
|  **Port Type**  |  **Trust State**  |  **Relayed Packet Type**  |  **Result**  |  **Reason**  |  
| --- | --- | --- | --- | --- |  
|  L2 Port  |  Untrusted  |  Unicast DHCP Offer/Ack  |  Dropped  |  DHCP Snooping prevents server messages on untrusted L2 ports.  |  
|  L3 Port  |  N/A (Routed)  |  Unicast DHCP Offer/Ack  |  Accepted  |  Routed ports are the intended nodes for Relay Agent communication.  |  
|  L2 Port  |  Trusted  |  Unicast DHCP Discover with option 82  |  Accepted  |  Trusted port allows all DHCP signals.  |  
|  L2 Port  |  Untrusted  |  Unicast DHCP Discover with option 82  |  Accepted  |  The packet with relay agent IP address and Option 82 is legitimate.  |  
|  L2 Port  |  Trusted  |  Unicast DHCP Discover without option 82  |  Accepted  |  Trusted port allows all DHCP signals.  |  
|  L2 Port  |  Untrusted  |  Unicast DHCP Discover without option 82  |  Dropped  |  The packet with relay agent IP address and no option 82 is rogue.  |
